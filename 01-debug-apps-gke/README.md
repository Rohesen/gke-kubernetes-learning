# 🔍 Debug Apps on Google Kubernetes Engine (GKE)

> **Google Cloud Skills Boost — GSP736**

This lab focuses on debugging applications running on **Google Kubernetes Engine (GKE)** using **Cloud Logging** and **Cloud Monitoring**.

The lab simulates a production-style troubleshooting scenario where an application contains an intentional configuration issue. The objective is to detect the problem using monitoring and logs, identify the root cause, fix it, and verify that the application is working correctly.

# 🧠 What This Lab Teaches

A typical production troubleshooting flow looks like this:

```text
Application
     ↓
GKE
     ↓
Application Logs
     ↓
Cloud Logging
     ↓
Logs-based Metric
     ↓
Cloud Monitoring
     ↓
Alert
     ↓
Troubleshooting
     ↓
Identify Root Cause
     ↓
Fix Configuration
     ↓
Deploy Updated Application
     ↓
Verify Application Health
```

The important idea is:

> **Logs tell us what happened, metrics tell us how often it is happening, and alerts tell us when we need to take action.**

# 📊 Task 4 — Create a Logs-Based Metric

Cloud Logging collects logs generated by the GKE workloads.

The logs can be used to create a **logs-based metric**.

A logs-based metric converts matching log entries into a measurable metric.

### Why use a logs-based metric?

Suppose an application produces errors like:

```text
HTTP 500
HTTP 503
Application Error
Connection Error
```

Instead of manually searching logs every time, we can create a metric that counts these events.

Conceptually:

```text
Log Entry
    ↓
Matching Filter
    ↓
Logs-Based Metric
    ↓
Metric Value
    ↓
Cloud Monitoring
```

### Example metric

The lab creates a metric related to frontend errors.

The metric is:

```text
Error_Rate_SLI
```

The metric can then be used by Cloud Monitoring.

---

# 🚨 Task 5 — Create an Alerting Policy

After creating the logs-based metric, create an alerting policy based on that metric.

The purpose of an alert is to automatically notify us when application behavior crosses a defined threshold.

### Example flow

```text
Frontend Error
      ↓
Cloud Logging
      ↓
Error_Rate_SLI
      ↓
Cloud Monitoring
      ↓
Threshold exceeded
      ↓
Alert / Incident
```

The alerting policy used in the lab monitors the frontend error rate.

A threshold can be configured so that an incident is created when the error rate becomes abnormal.

### Important concept

An alerting policy is basically:

> **If this condition becomes true, create an incident.**

# 🐛 Root Cause Analysis

The application contains an intentionally misconfigured component.

The error can be identified by correlating:

1. Cloud Monitoring alert
2. Logs-based metric
3. Cloud Logging entries
4. Kubernetes workload information
5. Pod/container logs

This demonstrates an important production troubleshooting principle:

> **Don't immediately restart the application. First identify the root cause using logs, metrics, and workload information.**

# 📚 Key Concepts

### 1. Cloud Logging

Cloud Logging collects logs from applications and infrastructure.

It helps answer:

> **What happened?**

---

### 2. Cloud Monitoring

Cloud Monitoring tracks metrics and application health.

It helps answer:

> **How is the system behaving?**

---

### 3. Logs-Based Metric

A logs-based metric converts matching log entries into numerical metrics.

For example:

```text
100 error logs
      ↓
Error Count = 100
```

---

### 4. Alerting Policy

An alerting policy watches a metric and creates an incident when a condition is met.

```text
Metric
  ↓
Threshold
  ↓
Condition
  ↓
Alert
```

---

### 5. Kubernetes Logs

Container logs help identify application-level problems.

```bash
kubectl logs <POD_NAME>
```

---

### 6. `kubectl describe`

`kubectl describe` provides detailed information about Kubernetes resources, including:

- Events
- Status
- Configuration
- Containers
- Volumes
- Scheduling information

Example:

```bash
kubectl describe pod <POD_NAME>
```

# 💡 Key Takeaways

- GKE applications should be monitored continuously.
- Logs are essential for troubleshooting application failures.
- Metrics provide a measurable view of system behavior.
- Logs-based metrics can convert application errors into monitoring signals.
- Alerting policies help detect problems automatically.
- `kubectl logs` is one of the most useful commands for application debugging.
- `kubectl describe` helps investigate Kubernetes resources and events.
- Monitoring and logging should be used together.
- Production troubleshooting should follow a structured process rather than random restarts.
- After fixing an issue, always verify the application and monitoring signals again.
